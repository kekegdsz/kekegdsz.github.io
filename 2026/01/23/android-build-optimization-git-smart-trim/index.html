Android 构建优化：从漫长编译到秒级反馈

智能任务裁剪与 Git 状态感知

kekegdsz 发布于 2026-01-23

本文首发于 掘金，欢迎转载时注明原文链接。

如何让 Gradle 自动感知代码变更，只编译真正需要修改的模块？下面是一套基于 Git 状态感知的智能构建优化思路与实践要点。

前言：构建慢的痛点

「又卡在编译了…」相信每个 Android 开发者都经历过这样的时刻。随着项目规模增长，每次只改几行代码却要等待漫长的全量编译，效率会明显下降。

传统增量编译有帮助，但在多模块项目里仍有很大优化空间。本文分享一套让 Gradle 尽量只编译变更相关模块的方案思路。

一、原理分析

1.1 传统构建的瓶颈

即使启用了增量编译，Gradle 仍可能：

  • 执行 lint
  • 运行单元测试
  • 处理所有模块的资源编译
  • 执行 kapt / ksp 等注解处理

1.2 优化思路概览

  1. Git 状态感知：识别仓库相对上次构建是否有「实质性」变更
  2. 任务裁剪：在可控前提下跳过与当前开发无关的任务
  3. 失败回退：裁剪导致失败时，下次回到更保守的策略
  4. 通用编译优化：Kotlin / Java / 测试并行等全局提速

2.3 智能任务裁剪

在 gradle.taskGraph.whenReady 中：

  • 仅在你关心的生命周期（例如 assemble*）里做裁剪
  • 根据 _gitHeadChanged、上次裁剪是否失败等，决定是否允许裁剪
  • 对 lint、test、connectedAndroidTest 等任务按需 enabled = false
  • 通过 git diff 解析变更文件路径，映射到 Gradle 子工程路径，再对未变更模块的 compileDebug* / kaptDebug* / kspDebug* 等任务选择性关闭

2.4 容错与回退

  • 构建开始前写入「本次可能失败」标记
  • gradle.buildFinished 里根据 result.failure 清理或保留标记
  • 一旦失败，下次构建自动走全量或保守路径，避免长期处在错误裁剪状态

四、效果预期（量级参考）

原文在约 10 模块、约 20 万行业务代码的测试工程中的对比（实际以你机器与工程为准）：

场景 传统构建 优化后 说明
单模块小改动 ~45s ~12s 明显缩短
跨模块 API 变更 ~52s ~52s 不宜过度裁剪
Clean 后全量 ~68s ~68s 与全量一致
日常迭代 ~38s ~15s 体感提升大

环境参考：MacBook Pro M1、16GB RAM、Gradle 7.4（升级 AGP/Gradle 后行为会变化，需重新摸底）。
